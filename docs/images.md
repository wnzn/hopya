# Private body and discussion images

Task bodies, new-task/subtask bodies, comments and replies have an **Image** toolbar action. Pasting or dropping image files uses the same uploader. The shared document discussion panel supports images too. Select an image in the editor to edit its description or remove the node. PNG, JPEG, GIF and WebP files are supported, up to 10 MiB each; the API checks raster containers and dimensions (16,384 pixels per side, at most 40 megapixels). It does not transcode images or run an antivirus scanner. SVG, HTML, data URLs, arbitrary paths and remote image URLs cannot render as body images. External-image HTML paste retains its text and reports that the image must be uploaded as a file.

## Saving and drafts

- Uploads use authenticated `POST /api/v1/workspaces/:wid/images`, with `kind` (`task-body`, `task-comment` or `document-comment`), `resourceId` when there is an existing target, and the ordinary attachment `{name,contentType,data}` base64 fields. Only a new task body's upload may omit `resourceId`.
- A successful upload returns a private `url`, a forced-download `downloadUrl`, and `expiresAt`. These contain opaque metadata IDs, never storage keys, credentials or bearer capabilities. Only the uploader, with current target permissions, can preview an uncommitted upload. At most 50 uncommitted uploads may be active per account.
- Inserted images use ordinary `![description](/api/v1/workspaces/.../images/.../inline)` Markdown. Task creation/body update or comment creation validates those references and claims pending images in the same transaction as the content and audit. A failed save keeps the draft and upload available for retry. Bodies have at most 100 image references. A new task does **not** have to be created before adding images.
- Task-body images become ordinary task attachments on commit, retaining the existing private download/list/delete workflow. Removing an image node from a saved body keeps its attachment available until explicitly deleted. A copied committed image URL retains its original resource/comment ownership; deleting the source comment or attachment revokes copied references too.
- Task drafts, comment drafts and separate reply drafts are kept in this tab's `sessionStorage`, scoped by account, workspace and target. Saved task recovery retains its baseline revision; a changed server version requires explicit reload/reconciliation. Browser-storage failures are visible. Drafts are cleared only after successful saving or an explicit discard. Closing a reply keeps its draft for reopening. Range-comment selections are not restored across a page reload; the recovered text can be posted as a general comment or attached to a freshly selected range.
- Uploading/failed files remain in this page's memory across composer close/reopen, with retry/removal controls. A late upload completion cannot insert an image into another task/reply. Files awaiting upload are **not** persisted across page reload or tab closure; the unload guard warns first. Successful upload references survive in the text draft, but uncommitted server uploads expire after **24 hours**, including when the browser remains open. Expired references reject saving explicitly and must be removed/reuploaded. Save/post controls wait for uploads and failed-insertion retries; body-length checks reject the entire over-limit edit instead of cutting an image URL.

## Permissions, bytes and cleanup

Body uploads require `items:read` and `items:write`; comment uploads require the target's read permission plus `comments:create`. Pending reads also require the uploader and current upload permission. Committed image reads require current membership and target read access, including after the storage read completes. Site administration does not bypass these checks. Private inline routes are `GET /workspaces/:wid/images/:imageId/inline` and the raster-only `GET /workspaces/:wid/items/:id/attachments/:attachmentId/inline`. Existing download paths remain forced `application/octet-stream` attachments. Inline MIME comes from bytes, with `nosniff`, `sandbox`, same-origin resource policy and `private, no-store` headers; no anonymous/public bucket or redirect is introduced.

Migration **0010_rich_text_images** is additive. It references the existing opaque-key `storage_objects` ledger and workspace/resource composite keys. Task/document/workspace deletion cascades metadata. Comment tombstoning immediately deletes its image metadata and revokes access; replies retain their independently owned images, and later permanent removal is safe. Discarded/expired drafts and failed upload compensation leave physical objects in the same bounded cleanup ledger. The collector expires up to 100 draft rows per sweep, preserves every live attachment/image reference, and retries failed physical or ledger deletion. Operators changing storage drivers must retain the existing backend cleanup guidance.

Workspace export **version 8** adds an `images` metadata array containing committed images only, alongside existing task `attachments`. Both service and snapshot-stream exports preserve IDs, owning resource/comment IDs, attachment link, filename, MIME, size and timestamps; document-comment entries require `documents:read`. No bytes, object keys, storage backend locations, pending drafts or secrets are exported. Task exports retain image Markdown. These private links require authentication on the original instance; a portable restore still requires a full database **and** private object-store backup.

## Gallery

Gallery reads the first rendered image from each task's body, excluding code examples and unsupported URLs. Multiple body images have named previous/next buttons, an announced position/description, no automatic cycling, and explicit loading/failure/retry states. Carousel controls and task-open buttons are separate controls. The existing bounded task rendering/grid layout remains; mobile carousel controls use 44px targets.

## Verification boundaries

Focused non-browser API and unit checks cover authorization, raster rejection, draft claim/audit rollback, comment tombstones, cleanup failures, safe export metadata, Markdown round-trip, Gallery image ordering and upload-queue retention. Rendered clipboard/drop behavior, browser draft recovery, carousel keyboard/focus behavior and physical mobile layout need owner-authorized browser verification. The existing AWS-SDK local S3 mock covers private signed storage, failure compensation and live revocation; operator S3 services and real device codecs require separate integration checks.
